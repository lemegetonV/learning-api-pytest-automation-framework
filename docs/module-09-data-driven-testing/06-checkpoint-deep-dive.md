# Module 09 Checkpoint Deep Dive

This checkpoint separates test behavior from test data. The test function still owns the scenario and assertions, but payloads, filter rows, and generated values move into clear data sources.

## Mental Model

Data-driven testing is a pipeline:

```mermaid
flowchart LR
  A["Data source"] --> B["Loader or generator"]
  B --> C["Parametrize cases"]
  C --> D["API request"]
  D --> E["Assertions"]
  E --> F["Readable case failure"]
```

The data source can be inline, JSON, CSV, or generated by Faker. The best choice depends on structure, readability, reproducibility, and how much variation the test needs.

## Execution Flow

For the JSON-file POST tests:

1. [`load_json_data`](../../src/utils/data_loader.py) reads [`post_payloads.json`](../../test-data/module_09/post_payloads.json) from a project-relative path.
2. `POST_PAYLOAD_CASES` is loaded at module import time.
3. `@pytest.mark.parametrize` creates one test case per JSON object.
4. The test posts `case["payload"]` through [`APIClient`](../../src/api_client/client.py).
5. Assertions compare status, generated ID, and every echoed payload field.

For CSV filter tests, [`load_csv_data`](../../src/utils/data_loader.py) returns strings because CSV has no native numeric types. The test converts `user_id` and `expected_count` to integers before using them.

## Code Walkthrough

[`src/utils/data_loader.py`](../../src/utils/data_loader.py) keeps file loading small and explicit. `project_path` resolves files from the repository root so tests do not depend on the current working directory. `load_json_data` preserves JSON types. `load_csv_data` returns a list of dictionaries with text values.

[`test_data_loader.py`](../../tests/learning/test_09_data_driven/test_data_loader.py) proves those loader assumptions directly.

[`test_static_file_data.py`](../../tests/learning/test_09_data_driven/test_static_file_data.py) shows how static JSON and CSV become parametrized API tests. The `_case_ids` helper makes pytest output show names such as `complete-post` instead of anonymous dictionary values.

[`test_generated_data.py`](../../tests/learning/test_09_data_driven/test_generated_data.py) introduces Faker through `build_fake_post_payload`. The seed is part of the test input so generated data is repeatable.

## Python And Framework Syntax To Notice

| Syntax | Why It Matters |
|---|---|
| `Path(__file__).resolve().parents[2]` | Finds the repository root from utility code |
| `json.load(...)` | Preserves nested structures and numeric JSON values |
| `csv.DictReader(...)` | Turns rows into dictionaries keyed by column name |
| module-level data constants | Load test data once for parametrization |
| `ids=_case_ids(...)` | Makes generated pytest cases readable |
| `int(row["user_id"])` | Converts CSV text into the type the API expects |
| `Faker().seed_instance(seed)` | Makes generated values deterministic |
| `for key, expected_value in payload.items()` | Validates echoed payload fields without duplicating assertions |

## Responsibility Boundaries

At this checkpoint:

- Data files own test inputs, not test logic.
- Loader helpers own file resolution and parsing.
- Test functions own conversions, requests, and assertions.
- Faker builders own realistic but reproducible generated values.
- Schema validation is still deferred to Module 10.
- Database-backed factories and persistent setup/cleanup are still out of scope.

Do not hide expected behavior inside the data file. A row can say `expected_count`, but the test should still express what that count means.

## Common Mistakes

- Treating CSV values as integers before converting them.
- Generating random data without a seed, making failures hard to reproduce.
- Putting assertions or business logic into the loader.
- Loading data from paths relative to the current shell instead of the project root.
- Using huge external data files that make failures unreadable.
- Assuming generated data is valid just because it looks realistic.

## Debugging And Failure Model

| Failure | Likely Cause |
|---|---|
| File not found | Wrong project-relative path or missing test-data file |
| JSON decode error | Invalid JSON syntax or trailing comma |
| CSV value mismatch | Header name typo or unconverted text value |
| Parametrized case hard to identify | Missing or weak `ids=` values |
| Generated data differs between runs | Missing seed or different Faker setup |
| API rejects generated payload | Generated value violates the API contract |

When a data-driven case fails, first identify the case ID, then inspect the exact input row or payload that produced it.
